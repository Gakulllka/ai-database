# Оркестрация агентов

Основной ИИ координирует работу: понимает цель, выбирает исполнителей, проверяет
результаты и интегрирует изменения. Для содержательной задачи делегируй
ограниченные подзадачи доступным субагентам. Для небольшой работы достаточно
одного исполнителя. Если хост не поддерживает делегирование или ограничивает его,
явно назови это ограничение и продолжай доступную часть.

## Контракт подзадачи

Передай исполнителю цель, нужные пути и ревизию, входные данные, критерии результата,
разрешённые действия и границы записи. Укажи корень проверенного Database или
установленной `.database/library`, чтобы он нашёл навыки своего пакета.
Результат должен содержать наблюдения, изменённые файлы, выполненные проверки и
оставшуюся неопределённость. Сохраняй этот короткий контракт в текущем плане;
отдельная доска нужна только для работы между сессиями.

Независимые исследования и проверки запускай параллельно. Для записей назначай
одного владельца на файл или изолированную рабочую копию. Зависимые этапы выполняй
после проверенного результата предыдущего. Основной ИИ разрешает конфликты и
сверяет итог с запросом пользователя. Независимый ревьюер получает весь фактический
diff и нужные источники, а не только пересказ автора.

## Выбор модели и рассуждения

Перед каждым запуском выбирай из моделей и уровней reasoning, доступных текущему
хосту. Для ограниченного поиска и классификации достаточно более быстрой модели
с умеренным рассуждением. Для реализации и тестов нужна модель, надёжная для
фактического стека. Для неоднозначных планов, безопасности и сложного ревью выбирай
более сильное рассуждение. Усложняй выбор при недостаточных доказательствах или
неудаче, а не по числу агентов. Не обещай выигрыш в скорости или качестве без замера.

В поставляемых ролях Database поля `model` и `model_reasoning_effort` намеренно
не закреплены. Оркестратор может передать их при запуске, когда API хоста это
поддерживает; иначе используются доступные настройки и наследование. Фиксированные
поля в пользовательской роли имеют собственный приоритет: сохраняй чужие настройки
и учитывай их при выборе. Инструкция внутри текста роли не переключает модель
уже работающего агента. Не меняй глобальную конфигурацию или провайдера ради
одной подзадачи.

Для именованной роли и явного выбора модели передавай компактный самостоятельный
контекст. В Codex с MultiAgentV2 полное наследование истории (`fork_turns=all`)
несовместимо с применением custom role; используй поддерживаемый запуск без полного
fork. При отсутствии такого управления не выдавай обычного субагента за запущенную
native-роль.

## Роли и права

| Пакет | Роли |
| --- | --- |
| common | explorer, docs-researcher, architect, planner, reviewer, database-curator |
| development | implementation-worker, language-reviewer, e2e-runner, security-reviewer, test-reviewer, build-error-resolver |
| 1c | 1c-reviewer, 1c-build-resolver |
| godot | godot-reviewer, godot-build-resolver |

Определения устанавливаются в `.codex/agents/*.toml`. Текущий Codex обнаруживает
standalone-файлы с `name`, `description` и `developer_instructions`; имя роли
совпадает с именем файла. Навыки остаются источником методики.

Architect предлагает варианты устройства решения и контракты между частями;
planner переводит выбранное решение в последовательность проверяемых шагов.
Оркестратор принимает решение в пределах требований пользователя и назначает
исполнителей. Для небольшой локальной правки достаточно короткого плана.

Implementation-worker пишет код и релевантные тесты в назначенной области.
Language-reviewer независимо проверяет фактический стек по его навыкам; для 1С
и Godot сохраняй доменных владельцев. E2E-runner проверяет собранный результат
в согласованном тестовом контуре и меняет только разрешённые тесты/артефакты.
Оркестратор принимает результаты, разрешает конфликты и выполняет интеграцию.
Для ошибок 1С и Godot используй профильного диагноста; общий build-error-resolver
не заменяет их. См. [профили исполнения](../../../development/docs/agents/execution-profiles.md)
при подключённом пакете development.

Права песочницы и approvals субагент наследует от родителя. Поле `sandbox_mode`
в файле роли и запрет записи в инструкции сами по себе не доказывают отдельный
read-only sandbox. Проверяй фактические разрешения хоста. Роль не расширяет доступ,
не разрешает установку инструментов, действия за пределами согласованного контура
или публикацию. Пишущие роли наследуют реальные разрешения хоста и получают от
оркестратора отдельную область записи; их TOML не расширяет права.

## Распределение работы

1. Explorer и docs-researcher собирают независимые факты. Оркестратор определяет
   фактический стек, требования, риск и границы задания.
2. При изменении границ модулей, хранения, API или жизненного цикла architect
   рекомендует варианты и контракты. Planner готовит порядок реализации.
3. Implementation-worker получает выбранный профиль, входной контракт, пути
   записи, допустимые команды/генерируемые артефакты и проверяемый результат.
   Независимые части можно выполнять параллельно после согласования интерфейсов.
4. Языковое, тестовое и security-ревью запускаются по затронутым рискам. Доменные
   ревьюеры имеют приоритет в своей области; не вызывай всех специалистов по списку.
5. После сборки E2E-runner проверяет нужные пользовательские сценарии. При сбое
   возвращает ожидаемый/наблюдаемый результат и доказательства. Оркестратор отдаёт
   исправление владельцу кода и повторяет затронутые проверки. E2E не чинит продукт
   самостоятельно и не ослабляет утверждения ради успешного прогона.

## Подключение и проверка

После `setup` выполни `check`, проверь установленные роли и сохранённые локальные
конфликты. Не перезаписывай чужой одноимённый TOML. Синтаксическая проверка,
обнаружение роли хостом и полезное выполнение подзадачи — разные доказательства;
укажи, какой уровень действительно проверен.
