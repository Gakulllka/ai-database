# Дизайн: выбор процесса и владельцы

Обновлено: 2026-11-10. Это оригинальная адаптация исследованных подходов к
существующим навыкам Database; сторонние пакеты, инструменты и ассеты не включены.

## Выбор по результату

- [design-workflow](../../skills/design-workflow/SKILL.md) — короткий вход для
  неопределённой или смешанной задачи. Определяет цель, аудиторию, обязательное,
  необязательное, исключения, сохраняемые свойства и доказательства приёмки.
- [character-art-direction](../../skills/character-art-direction/SKILL.md) —
  выразительность, привлекательность и согласованность образа персонажа.
  Иллюстрация, reference sheet и игровой ассет имеют разные требования.
- [Функциональный UX](../../skills/frontend-design-direction/references/functional-ux.md)
  расширяет существующий `frontend-design-direction`: операция, данные для
  решения, действия, состояния и проверяемые сценарии для форм и инструментов.
  Отдельного дублирующего functional-design skill нет.

При точной задаче сразу используй владельца; маршрутизатор не требует нового
интервью и не переоткрывает согласованный дизайн. Для игры разделяй арт обложки,
читаемость игровых ассетов и взаимодействие HUD/меню, сохраняя общий визуальный язык.

## Что переиспользовано

| Владелец | Ответственность |
| --- | --- |
| `frontend-design-direction` | Визуальное направление веба, общий функциональный UX, web finish gate |
| `design-system` | Токены, канон, DESIGN.md и визуальные образцы |
| `ecosystem-design-consistency` | Согласованность существующего канона между продуктами |
| `1c-managed-forms` и существующий `form-patterns` | Нативная компоновка и редактирование форм, привязки, ID и обработчики |
| `godot-ui-input` | UI движка, ввод, фокус, масштабирование и взаимодействие |
| `godot-assets-pipeline` | Импорт, технические ограничения и проверка игровых ассетов |
| Доступный image-generation skill | Механика генерации и редактирования изображений |

Техническая валидация, визуальная оценка и проверка поведения не взаимозаменяемы.
HTML-макет не подтверждает работу формы 1С. Reference sheet не подтверждает
пригодность модели к анимации. Оценка агента не доказывает рост продаж.
При отсутствии нужной среды результат остаётся предложением с явными ограничениями.

## Подключение и сопровождение

Канонические инструкции находятся в `skills/`, проекции Codex — в `.agents/skills/`.
Для четырёх навыков `design-workflow`, `character-art-direction`,
`frontend-design-direction`, `design-system`:

```text
node scripts/design/sync-skills.js --write
node scripts/design/sync-skills.js --check
node tests/scripts/design-workflows.test.js
```

Изменённые `1c-managed-forms` и `godot-ui-input` синхронизируются существующими
`scripts/1c/sync-skills.js` и `scripts/godot/sync-skills.js`.
В выборочном каталоге группа `capability:design-workflows` устанавливает четыре
дизайн-навыка. Модули `framework-language`, `1c-development` и `godot-development`
зависят от этой группы; два существующих дизайн-навыка имеют единственного
владельца `design-workflows`, а не копируются между модулями.
При отдельной установке арт-процесса наличие всех движков и генераторов не
предполагается: выбирай только доступный и подходящий платформенный навык.

## Проверка поведения

Помимо метаданных, регистрации, ссылок и проекций, проверяй решения на реальных
коротких поручениях: обработка сверки 1С, плотная таблица инструмента, арт обложки,
игровой спрайт в реальном масштабе и локальная правка существующего персонажа.
Независимый проход получает исходные условия и актуальные инструкции без
подсказанного ответа. Сохраняй локальные результаты отдельно от распространяемой
библиотеки. Такие проверки оценивают решения агента; они не являются запуском
1С, проверкой движка или исследованием предпочтений аудитории.
