# Профили проверки кода и E2E

Основной ИИ выбирает профиль по фактическому стеку модуля и нужному результату.
Передавай корень проверенного Database или установленной `.database/library`.
Пути к навыкам начинаются с имени пакета. Роли используют права и настройки
подтверждений хоста. Модель и уровень рассуждения выбирает оркестратор при запуске.
[Порядок оркестрации](../../../common/docs/agents/orchestration.md).

## Проверка кода на конкретном стеке

Зови [language-reviewer](../../codex-agents/language-reviewer.toml), когда
корректность изменения зависит от языка, рантайма или API фреймворка. Передай
пути и diff или диапазон ревизий, затронутые контракты и известные версии.
Ревьюер сверяет выбор с конфигурацией затронутого модуля. Для полиглотного
проекта укажи, к каким модулям относится каждый стек.

| Объявленный стек | Где уточнить версии и настройки | Навыки и предмет проверки |
| --- | --- | --- |
| C#/.NET | `.csproj`, `global.json`, общие файлы MSBuild, объявленные зависимости и CI | Nullability, владение ресурсами, отмена асинхронных операций, время жизни зависимостей и совместимость API по [dotnet-patterns](../../skills/dotnet-patterns/SKILL.md). При проверке применимых C#-тестов используй [csharp-testing](../../skills/csharp-testing/SKILL.md). |
| JavaScript/TypeScript | `package.json`, lockfile, `tsconfig.json` при наличии, объявленные версии рантайма и сборки | Границы модулей, проверка входных данных во время выполнения и асинхронные ошибки по [typescript-patterns](../../skills/typescript-patterns/SKILL.md). Для TypeScript учитывай настройки компилятора модуля. |
| Python | `pyproject.toml`, объявленные версии интерпретатора, зависимости и CI | Обработка исключений, очистка ресурсов, конкурентность и совместимость по [python-patterns](../../skills/python-patterns/SKILL.md). Для pytest используй [python-testing](../../skills/python-testing/SKILL.md). |

Для другого стека используй установленные навыки, которые подходят модулю, и
укажи, где профильного знания или доказательств не хватило. Для BSL и метаданных
1С используй [1c-reviewer](../../../1c/codex-agents/1c-reviewer.toml), для кода,
сцен и жизненного цикла Godot — [godot-reviewer](../../../godot/codex-agents/godot-reviewer.toml).

Ревьюер читает код, конфигурацию, тесты и имеющиеся результаты. Правки, установки
и запуск кода выходят за рамки этой роли. Для каждого существенного замечания
укажи файл и строку, путь выполнения, условие, наблюдаемое или ожидаемое последствие
и точечное исправление. Если замечаний нет, обозначь проверенную область и пробелы.

## Проверка сценария на работающей системе

Зови [e2e-runner](../../codex-agents/e2e-runner.toml), когда нужно подтвердить
конкретный сценарий через реальный вход приложения. Передай ревизию или сборку,
среду и цель, сценарии с ожидаемыми результатами, тестовые данные и разрешённые
действия. Укажи существующий runner или UI-инструмент, разрешённый запуск и
очистку, каталоги артефактов и конкретные тестовые файлы, если их можно менять.

| Платформа | Входные данные и методика | Что подтверждает сценарий |
| --- | --- | --- |
| Web | Тестовый URL, браузер и тестовый профиль. Используй существующий runner, например Playwright, или разрешённую браузерную сессию. Сверь режим выполнения и места передачи данных. [e2e-testing](../../skills/e2e-testing/SKILL.md), [browser-qa](../../skills/browser-qa/SKILL.md). | Пользовательское действие приводит к ожидаемому состоянию. Для визуальной сверки используй согласованный эталон. |
| Windows desktop | Путь к сборке, нужный процесс и окно, изолированный профиль. Для штатной UI Automation проверь стабильный идентификатор элемента и дождись нужного состояния. [windows-desktop-e2e](../../skills/windows-desktop-e2e/SKILL.md). | Указанное окно или диалог после действия показывает нужное состояние или результат операции. |
| 1С | Версия платформы, клиент, изолированная тестовая информационная база и разрешённый тестовый пользователь. Выполни сценарий существующим средством проекта и зафиксируй ожидаемые бизнес-значения. [1c-testing](../../../1c/skills/1c-testing/SKILL.md). | Отдельно фиксируй запуск или открытие формы и проверенный бизнес-результат, например итог расчёта либо статус проведения. |
| Godot | Версия движка, проект или сборка, целевая платформа, изолированные тестовые данные и существующий сценарий. Сверь результат проверки поведения с ожидаемым и проверь журналы выполнения. [godot-testing](../../../godot/skills/godot-testing/SKILL.md). | Headless-запуск подтверждает проверенную логику или сцену. Изображение, звук и аппаратный ввод проверяй на подходящей цели. |

Runner выполняет разрешённые действия в изолированной среде. Область записи
включает только назначенные тестовые файлы и артефакты. Разрешённые изменения
тестового состояния и очистку ограничивай назначенными ресурсами. Правка кода
продукта, глобальные установки, облачные выгрузки, работа с боевой средой и
данными клиентов выходят за рамки роли. Сохраняй минимальный объём артефактов.
Удаляй секреты из выдаваемых команд, логов, скриншотов и трасс или оставляй такие
материалы закрытыми. Перед повтором сценария с записью сверяй оставшееся состояние
и границы тестовых данных. Сохраняй первую ошибку и результат ограниченного повтора.

В отчёте укажи команду без значений секретов или шаги UI, цель, ревизию и версию,
ожидаемый и фактический результат, статус каждого сценария, код завершения или
тайм-аут, пути к доступным доказательствам и изменённым файлам. Если среда,
инструмент или разрешение недоступны либо проверка результата не запускалась, пометь
проверку как неподтверждённую.
